# TEAS 1 -- UI Surface, Feature Inventory and UX Smells (discovery 01)

> Purpose: feature-parity checklist + UX design input for TEAS 2 (same feature set and tax-posting behaviour, more accounting flexibility, much better UX).
> Method: read-only static analysis of `frontend/app/**`, `frontend/components/**`, `frontend/lib/**`, `frontend/messages/th.json`, `frontend/package.json`, `docs/manual/**`, `docs/Design(UI).md`, `design/component-patterns.md`; plus prior role-based UX reviews (`_review/ui-*.md`, `swarm-findings/**`) as corroboration only.
> Repo state analysed: branch `chore/release-2.5.0` (backend 2.5.0, cancel+reissue sales documents).
> All paths are repo-relative to `Y:\ClaudePlayground\TEAS-Project`. No secrets were copied.
> Thai labels are quoted from `frontend/messages/th.json`. "BE" = Buddhist Era.

## Executive summary

**What this is.** A read-only inventory of the TEAS 1 frontend (108 pages, 19 route handlers, 87 components, ~38.5 K lines of TS / TSX / CSS) plus the Thai user manual (46 sections), cross-checked against the backend where UI behaviour depends on it. Use section 2 as the **feature-parity checklist**, section 3 as the **form-by-form field spec**, section 5 as the **UX problem list**, and the appendices for business rules, stale documentation and a flat parity checklist.

**Stack reality (section 4).** Next.js 15 / React 19 client-rendered app (102 of 108 pages are `'use client'`) behind a BFF proxy with an httpOnly-cookie JWT; Tailwind 3 + **DaisyUI 4 with ~87 hand-rolled components - not shadcn/Radix** (10 npm dependencies are unused: 5x Radix, cmdk, framer-motion, recharts, date-fns, cva); TanStack Table (client-side only) and Query (one 2,378-line `queries.ts` with 214 hooks); react-hook-form + zod in only 15 files (the rest are ad-hoc `useState`); next-intl with a Thai-default cookie locale; server QuestPDF documents plus RD AcroForm tax-form fillers; DaisyUI dark / blue themes exist but cannot be selected.

**The three owner-confirmed pain points, quantified (section 5.1).**
- **Slow creation:** a one-line tax invoice costs **7 clicks + 2 searches** (payment voucher **14 clicks + 3 entries over 3 page loads and usually 2 people**); no type-ahead, no shortcuts, no Enter-to-add-line; the 3fr / 2fr create layout leaves the line table ~520-760 px wide on common laptops (< ~1700 px), so price / VAT / total sit behind a horizontal scrollbar next to a permanent A4 preview.
- **Inconsistent pages:** 3 detail-page shells (`DocActionBar` is used by the 8 sales documents and by no purchase page), 3 line editors with 4 VAT idioms, 4 confirm dialogs, 5 error presenters, RHF vs `useState`, different lists (SO / DO have no create button; only PO has a row-action column; VI sorts by number), hard-coded Thai / English strings, raw ISO dates.
- **No editing after approval / posting:** of 16 transactional document types, **4 cannot even have their Draft edited in the UI (DO, CN/DN, PV, VI)** and **9 have no correction path once issued**; only TI and RC have cancel-and-reissue (since release 2.5.0); **no purchase document can be corrected after posting**. DB triggers protect only journals, tax invoices, vendor invoices, receipts and CN/DN - everything else is an application-level choice (matrix in 5.1.3).

**Highest-risk defects found** (all with evidence in 5.2): CN/DN print calls a PDF route that does not exist; DO -> TI creates AND posts a fiscal invoice in one click; TI form totals ignore line discounts; receipts can only be "Transfer"; a Posted PV may be offered "create VI" (double booking, static); quotation approve is gated on an API-key-only scope; failed or forbidden requests render as empty lists / zero tiles; `btn-danger` (14 destructive buttons) is not a real class so they look neutral; browser print of any report is blank.

**Parity must-keeps (section 2 / Appendix A).** The full Thai tax chain (Q -> SO -> DO -> BN -> TI -> RC -> CN/DN; PO -> VI -> PV -> 50ทวิ), VAT vs non-VAT company modes, WHT (per-line types, gross-up modes, foreign vendors, ภ.พ.36 reverse charge), RD form output (ภ.พ.30 / 36 / 01 / 09, ภ.ง.ด.1 / 1ก / 2 / 3 / 50 / 51 / 53 / 54, 50ทวิ, สปส.1-10, RD Prep `.txt`), payroll (PIT, SSO, payslips), bank-statement import and matching, manual journals, chart-of-accounts, period / year close, fixed assets + depreciation, expense claims, per-document activity log and original / copy print tracking, cancel-and-reissue, the agent-draft (MCP / OAuth "TEAS Connect") approval flow, multi-company + 12 seeded roles / ~91 permissions, number-gap audit.

**Flexibility gaps to design in (Appendix C).** Approval inbox; back-dating inside an open period; purchase-side cancel / reissue and vendor credit / debit notes; reversing / recurring journals; bulk actions, export and saved views; VAT output / input registers page; multi-currency; configurable GL-account mapping, document prefixes, branches, tax codes and expense-category defaults (all backend-only today); line-based credit notes; richer bank matching; classified financial statements with drill-down.

**Method and caveats.** Six parallel read-only passes (sales; purchases; master / bank / payroll / GL; reports / tax; settings / auth / platform; prior UX reviews) followed by spot-verification of the highest-impact claims. Items tagged **[static]** were inferred from code, **[calc]** from layout classes, **[verify]** are plausible but unconfirmed at runtime; nothing was executed. The earlier role-based test rounds were run by scripted agents, not human users. Manual and RBAC-guide statements that no longer match the code are listed in Appendix B.

### 1.4 Gating model

- **Permission codes** come from `GET /me/permissions` (`useMePermissions`) -- `{isSuperAdmin, permissions[]}`. `SidebarNav` filters with `!perm || isSuperAdmin || perms.includes(perm)`, `vatOnly` needs `/system/info.vatMode===true` (default hidden until known -- fixed S1 flash), `superAdminOnly` needs the flag.
- **Buttons:** `PermissionGate scope="..."` HIDES write actions (89 usages) and `useHasScope/useScopeState` (37 usages, 37 distinct scopes). Exception (F6, 2026-08-16): the five document-chain *convert* buttons render DISABLED with a "ต้องมีสิทธิ์ {perm}" tooltip instead of hiding.
- **Page level:** only some `/new` pages and settings pages render an inline "no access" block (19 pages, each copy-pasting the same markup); other pages rely on the BE 403 and `QueryState`.
- **VAT mode:** non-VAT companies lose Tax Invoice, Credit Note, Debit Note, ภ.พ.30 (nav + buttons + paper-document VAT rows); Receipt switches from "reference tax invoice" to "cash / reference invoice" mode.
- **Seeded roles** (12): SUPER_ADMIN, COMPANY_ADMIN, CHIEF_ACCOUNTANT, ACCOUNTANT, AR_CLERK, AP_CLERK, SALES_STAFF, PURCHASING_STAFF, WAREHOUSE_STAFF, APPROVER, AUDITOR, TAX_OFFICER (`docs/manual/rbac-ui-guide.md`). Visibility highlights (VAT company): WAREHOUSE_STAFF sees only Dashboard + Documents + Company profile; AUDITOR/TAX_OFFICER get read-only reports, number gaps, WHT certs, ภ.พ.30; APPROVER sees PO/PV/outstanding PO/AP aging with approve buttons; Roles/Users/API keys admin = COMPANY_ADMIN + SUPER_ADMIN; Companies (tax config) = SUPER_ADMIN only.
- **Stale doc warning:** the generated RBAC UI Guide predates at least these nav items and so does not cover them: bank accounts, bank reconciliation, expense claims, fixed assets, depreciation, journals, chart of accounts, period close, balance sheet, general ledger, AR aging, customer statement, vendor ledger.
- **E2E sentinel:** hidden `data-testid="nav-gates-ready"` appears once both gate queries settle.

### 2.4 Sales documents (30 pages)

Abbreviations: Q = ใบเสนอราคา, SO = ใบสั่งขาย, DO = ใบส่งของ, BN = ใบแจ้งหนี้/ใบวางบิล (route `/invoices`, API `billing-notes`, number prefix `IV`, paper title "INVOICE"), TI = ใบกำกับภาษี, RC = ใบเสร็จรับเงิน, CN/DN = ใบลดหนี้/ใบเพิ่มหนี้. DAB = `DocActionBar`, PM = `PrintMenu`, PCD = `PostConfirmDialog`, CAD = `ConfirmActionDialog`, CDM = `CancelDocumentModal`.

**Corrections to common assumptions**
1. `/documents` is NOT a sales hub - it is a static catalogue of Revenue Department (RD) tax forms (`D/documents/page.tsx:26-149`, data `L/rd-forms.ts`). The only "chain view" is the `DocumentChain` side rail on every detail page.
2. **SO and DO create forms have no UI entry point** (no list button, no dashboard action, no link anywhere; only e2e uses `page.goto`). Q, BN, TI, RC, CN/DN do have list create buttons.
3. Every server-side conversion creates a DRAFT, **except DO->TI, which creates AND posts the TI in one click** (see 5.2 SALES-H1).
4. Cancel / reissue (release 2.5.0) covers BN (cancel only), TI and RC (cancel, cancel-and-reissue, reissue, discard replacement). Q has its own inline cancel. SO, DO, CN and DN have no cancel at all.
5. Number format `MM-YYYY-<PREFIX>-<BU code>-NNNN`, prefixes QT, SO, DO, IV, TI, RC, CN, DN; sequence per BU and per month of the document date (`docs/manual/generated/chapter-04.md:227`).

- **Detail anatomy (all 8 detail pages):** `PageHeader` title "<ชื่อเอกสาร> <docNo|#id>" + PM; agent badge/banner (Q, TI, RC only); cancel / replacement banners (TI, RC via CDM `C/documents/CancelDocumentModal.tsx:108-153`; BN inline); DAB = status badge ("ร่าง . ### 2.13 Print / PDF / export mechanics (end to end)

- `openPdf(path)` fetches `/api/proxy/<path>`, makes a blob URL and `window.open`s it (filename lost; popups can be blocked, `L/api.ts:171-178`). `downloadFile(path, name)` = blob + synthetic `<a download>`. `printPdf` is used only by `PrintMenu` and `ChainRowPrint` (documents), never reports; it calls `window.open` AFTER an `await fetch`, so Safari / Firefox popup blockers can drop it.
- File-endpoint errors throw `ApiError` with Thai fallbacks (422 "ไม่มีข้อมูลสำหรับเงื่อนไขที่เลือก", 5xx "เชื่อมต่อไม่สำเร็จ...", 404 "ไม่พบไฟล์ที่ต้องการ"); callers then display them three different ways (`errorToToast`, `apiErrorToast`, raw `e.message` / `'Error'`).
- **No XLSX anywhere** - "Excel" means CSV. FE CSV = Blob with `﻿` BOM + shared `csvCell` (CSV-injection guard) on 5 reports (TB, BS, P&L, AP aging, bank rec); server CSV (UTF-8 BOM, CRLF) for AR aging and GL. No list-level export for any document list.
- **Browser print of any report page prints a BLANK page**: `app/globals.css:157-164` hides `body *` and reveals only `.paper-wrap`; no report or filing page uses `.paper-wrap` / `.no-print` (only payroll's SSO schedule opts in via `.sso-schedule-print`).
- Backend QuestPDF documents: all transaction documents, GL export (`GeneralLedgerPdf`), financial statements (`FinancialStatementPdf`), payslips, SSO part 1. Government forms: RD AcroForm overlay PDFs (see 2.10).

### 3.2 Sales document forms

**Common to Q / SO / BN / TI / RC / CN-DN:** customer* (zod positive int; inline error `pickCustomer` "เลือกลูกค้าก่อน"; CN/DN has no customer field - snapshotted from the TI server-side); BU; lines as in 3.0; notes. Line rules: description min 1, qty > 0, price >= 0, taxRate 0..1, at least 1 line ("ต้องมีรายการอย่างน้อย 1 รายการ"). Client previews use unrounded JS floats; the server rounds every step to 2 dp away-from-zero (`gross = round(qty x price)`, `net = round(gross x (1 - d%))`, `vat = round(net x rate)`; header totals are sums of the per-line results - `BE/Infrastructure/Sales/QuotationChainServices.cs:20-34`, `TaxInvoiceService.cs:845-903`), so previews can differ by a satang. Nothing clamps discount to 100%.

**Quotation (`components/forms/QuotationForm.tsx`)** - header: customer*, วันที่* (default today, editable), ยืนราคาถึง* (default +30 days, server requires >= docDate), BU; currency THB / rate 1 hard-coded. Lines: full (discount %, UoM, tax code). Totals: gross, discount (negative), VAT (only if vatMode), total. No prefill. Edit mode reverse-derives `taxRate` from `taxAmount / lineAmount`. Preview: PaperDocument with `validUntil` and label "ยืนราคาถึง". Create: [บันทึกร่าง] -> POST -> list; [ออกใบเสนอราคา] -> POST then `POST quotations/{id}/send` (assigns the QT number, **no confirm dialog**) -> detail. If step 2 fails the draft remains and a retry creates a second draft. Edit: single [บันทึก] (PUT -> detail).

**Sales order (`SalesOrderForm.tsx`)** - header: customer*, วันที่*, กำหนดส่ง (optional), BU. Lines as Q. Totals: subtotal + VAT + total (no discount row). Known gap (`:57-63,85-88`): `SalesOrderDetail` does not return expected-delivery date or notes, so edit mode starts them empty and the PUT replaces them (a hard-coded Thai warning is shown). Create: [บันทึกร่าง] -> list; [ยืนยันสั่งขาย] -> POST then `/post` (assigns SO number, no confirm) -> **list** (Q / BN land on detail).

**Delivery order (`DeliveryOrderForm.tsx`)** - non-RHF. Header: customer*, วันที่ส่ง* (default today), BU. Lines: bespoke table description*, qty (> 0), UoM; payload per line `unitPrice 0, discountPercent 0, taxCode 'VAT0', taxRate 0, productId null`. ### 5.1 The three owner-confirmed pain points

#### 5.1.1 P1 - Slow document creation

**Counting rules.** Counts are the MINIMUM number of user actions on the happy path, derived from the code (not timed). *Click* = mouse click / tap; *type* = one keyboard entry into a field or search box; navigation clicks are included. Scenario TI: VAT-registered company, existing customer, existing service product with a default price, company does not force a BU, entry from the dashboard quick-action. Scenario PV: VAT-registered company, existing juristic VAT-registered vendor, one service line with 3% withholding, no BU rule, payment by transfer, entry from the dashboard quick-action.

| Step | Typical TAX INVOICE (1 line) | Typical PAYMENT VOUCHER (1 line, WHT 3%) |
|---|---|---|
| Open the form | dashboard quick-action "ออกใบกำกับภาษี" = **1 click** (via sidebar + list button = 2) | quick-action "สร้างใบสำคัญจ่าย" = **1 click** (sidebar route = 2) |
| Party | click "เลือกลูกค้า" -> modal -> **type** search -> click result = **2 clicks + 1 type** (`components/create/PartySelectBox.tsx`, `components/ui/EntityPickerModal.tsx`) | click "เลือกผู้ขาย" -> modal -> type -> click = **2 clicks + 1 type** |

**Why it is slow (evidence)**

1. **No inline type-ahead anywhere.** The description box is free text; typing never suggests products - the product is chosen only through the magnifier modal, and editing the text afterwards drops the product link and its tax lock (`components/forms/ProductPicker.tsx:50-60`, `components/ui/LineItemsTable.tsx:153-154`). Customers and vendors are also modal-only (`PartySelectBox`); the customer "create new" link opens a NEW TAB. The original design promised debounced autocomplete dropdowns and keyboard shortcuts (`docs/Design(UI).md` 7.2: Ctrl+S save, Ctrl+P post, `/` focus search) - none exist (only Escape on three modals).
2. **The line grid does not fit the screen it sits on** [calc]. `DocumentCreateLayout` gives the form 3fr of a 3fr/2fr grid and a permanent A4 live preview 2fr (`components/create/DocumentCreateLayout.tsx:41`); the content area is `viewport - 256 px sidebar - 64 px padding` (`app/(dashboard)/layout.tsx:63`, `components/app-shell/SidebarNav.tsx:230`); the SectionCard adds 40 px of padding; the line table is `min-w-[760px]` and its declared column widths add up to ~980 px (240 min description + 80 + 96 + 128 + 80 + 192 + 128 + 40 - `LineItemsTable.tsx:132-142`). Result: visible table width is ~521 px at 1280, ~573 px at 1366, ~617 px at 1440, ~675 px at 1536, ~714 px at 1600 and ~762 px at 1680; with the sidebar collapsed it is ~683 px at 1366. **Price, discount, VAT, total and the delete button sit behind a horizontal scrollbar on every common laptop width**; the preview the user does not need while typing keeps 40% of the screen.
3. **Numeric fields fight the user.** `AmountInput` is a native `type=number` that coerces empty / invalid input to 0, so the field cannot be cleared (typing after selecting "0" works only by overwrite), has no thousands separators and rejects negatives (`components/ui/AmountInput.tsx:29-32`); PV / VI / EC / FA use raw number inputs instead (inconsistent).
4. **Save-then-confirm doubles the work and the risk.** TI, RC, CN/DN and VI "Post" first create a draft (network call 1) then open a confirm dialog (call 2 on confirm); closing the dialog leaves a saved draft and a form that will create ANOTHER draft on the next click (`components/forms/TaxInvoiceForm.tsx:218-225`; VI `app/(dashboard)/vendor-invoices/new/page.tsx:239-246`). Q / SO / BN "issue" do POST + issue in sequence with a failure window between.
5. **Approval is a separate stage on a separate page, with no inbox.** PO (create -> approve -> then VI / PV), PV (create -> approve -> post), EC (create -> submit -> approve -> pay), payroll (create -> approve -> post -> pay). An approver must hunt for drafts in list pages (earlier swarm test: about 40 list polls in 27 minutes to catch 3 vouchers) (`docs/manual/rbac-ui-guide.md`; 5.4 U-06).
6. **Defaults are missing or wrong, so the user re-decides every time.** WHT type is picked by hand on every line although category / product / vendor defaults exist in the API (`lib/expense-category-shape.ts:21-30`); PO "expected delivery" defaults to TODAY (`PurchaseOrderForm.tsx:111`); manual BN due date is +30 days regardless of the customer's credit term, while conversions use the term (`BillingNoteForm.tsx:124` vs `BE/Infrastructure/Sales/BillingNoteService.cs:112-115`); receipt applied amount defaults to the invoice TOTAL, not the outstanding balance, and the payment method is hard-coded to Transfer (`ReceiptForm.tsx:367,604-613`); no per-user default BU / bank account / payment method; VI default VAT rate 7% is hard-coded (`vendor-invoices/new/page.tsx:37`).
7. **Conversions do not carry enough.** PO -> PV prefills lines but not category or WHT and persists no link (`purchase-orders/[id]/page.tsx:143-151`); PO -> VI replaces all rows; TI -> CN/DN has no entry button (the `?fromTaxInvoiceId` prefill exists but nothing links to it); SO / DO create forms have no entry point at all (5.2 SALES-H6).
8. **Attachments cannot be added while creating** (detail page only), so a vendor invoice is saved, posted and later flagged "ไม่สมบูรณ์" until the user comes back to upload the tax-invoice file (`components/attachments/AttachmentsSection.tsx`, 5.4 M8).
9. **Dates are locked to "today"** on TI, RC, CN/DN, PV, VI, PO (server re-pins at post), so month-end catch-up entry and historical imports cannot be dated correctly through the UI; owner-approved back-dating inside an open period (`specs/doc-lifecycle-cancel-reissue-backdate.md`) is not shipped (5.4 U-24).
10. **No reuse tools**: no duplicate / "copy from", templates, recurring documents, bulk import or paste-from-spreadsheet (zero hits for duplicate / recurring / template in the frontend).

**Design targets for TEAS 2 (proposals, not measured):** keyboard-first entry (type-ahead for party and product with Enter to accept, Tab through qty / price / VAT, Ctrl+Enter = save, Ctrl+Shift+Enter = save and post); preview as an optional side drawer, default closed below ~1700 px; one-step "save and post" that never leaves an orphan draft; defaults from customer / vendor / product / category / last document; a visible "what is missing" summary; inline approve + post for users who hold both permissions, and an approval inbox for those who do not; duplicate / recurring documents.

#### 5.1.3 P3 - Documents cannot be edited once approved / posted

**The rule as built.** `docs/accounting-system-plan.md` section 3.2: a posted fiscal document is immutable, "no edit / delete path"; corrections go through a credit note (ม.86/10) or cancel + reissue; enforced twice - by application services (no mutate path) and by database triggers on critical post-fields. Numbers are assigned only on post / issue, are never reused, and a voided document keeps its number; `doc_date` is "today in Asia/Bangkok", never user input. The law (ม.86/4, ม.86/9-10, gap-free numbering) only requires this for ISSUED TAX documents - TEAS 1 applies the same freeze to most internal and commercial documents too, and gives them no replacement path.

**Where it is enforced (three layers)**
1. **UI:** the Edit button is simply not rendered once the status leaves Draft; the `/edit` route calls `router.replace(detail)` during render for non-Draft documents (Q, SO, BN, TI, RC, PO, EC, FA); there is no `/edit` route at all for DO, CN/DN, PV, VI, journals.
2. **API / domain:** `PUT` returns a domain error - `quotation.cannot_edit_after_send` (`BE/Infrastructure/Sales/QuotationChainServices.cs:198`), `so.cannot_edit_after_post` (`.../SalesOrderDeliveryServices.cs:90`), `billing_note.cannot_edit_after_issue` (`.../BillingNoteService.cs:258`), `ti.cannot_edit_after_post` (`.../TaxInvoiceService.cs:573`), `rc.cannot_edit_after_post` (`.../ReceiptService.cs:445`), `po.not_draft` (`BE/Infrastructure/Purchase/PurchaseOrderService.cs:177`), `vi.not_draft` (`.../VendorInvoiceService.cs:288`), `expense_claim.not_editable` (`BE/Infrastructure/Expense/ExpenseClaimService.cs:200`), `fixed_asset.not_editable` (`BE/Infrastructure/FixedAsset/FixedAssetService.cs:156`), `payroll.not_draft` (`BE/Infrastructure/Payroll/PayrollRunService.cs:158`), `replacement.locked_field` (`.../TaxInvoiceService.Cancel.cs:262`, `ReceiptService.Cancel.cs:324`); for some documents there is simply no endpoint (verified by listing `MapPut` / `MapDelete` per endpoint file: **no PUT or DELETE for Delivery Order and Payment Voucher; no PUT for CN/DN; no DELETE for SO, PO, VI, EC**).
3. **Database triggers (fiscal documents only):** header critical fields frozen once status is not DRAFT for journal entries (`020_journal_immutability.sql`), tax invoices (`040`, tightened by `583`, `643`: only POSTED -> VOIDED is a legal status change), vendor invoices (`060`; settlement fields deliberately NOT frozen), receipts (`570`, `643`), credit / debit notes (`571`, plus a no-delete-when-posted trigger); line tables frozen for TI, VI, RC and journal lines (`580`, `582`: also blocks re-parenting a line); audit log append-only (`030`, `584`). Files: `backend/src/Accounting.Infrastructure/Migrations/SqlScripts/`. **There is NO DB trigger for quotations, sales orders, delivery orders, billing notes, purchase orders, payment vouchers, expense claims, fixed assets or payroll** - for those the freeze is application-level only, i.e. a product choice, not a legal necessity.

**Why it hurts (symptoms, with the 2.5.0 example).** The 2.5.0 flow for correcting a customer name on a paid invoice is cancel RC -> cancel-and-reissue TI -> post replacement -> reissue RC (`specs/cancel-reissue-sales-docs.md`); the replacement form still lets users type into amount fields that the server then rejects; the user cannot choose the replacement's date; a PV typo costs a cancel + full retype of a voucher that already carries WHT choices; an approved PO with a wrong quantity must be cancelled (number consumed) and re-created; a posted VI or PV with a wrong WHT type has no UI fix at all; and the Edit button simply disappears, with no explanation or CTA ("why is this locked and what do I do?").

**TEAS 2 implications**
1. Split *legal immutability* (issued tax documents: number, date, parties' tax identity, amounts, tax) from *workflow locks* (everything else). Freeze only the former; let descriptive fields (notes, attachments, internal reference, BU, due date, payment terms) stay editable with an audit trail.
2. One correction toolkit for EVERY document family: edit while Draft (including DO, CN/DN, PV, VI); send-back / un-approve before posting (PO, PV, EC, payroll) with audit; cancel (void with reversal) with reason codes; cancel-and-reissue with locked fiscal fields; credit / debit notes on the purchase side too; reverse / copy-as-new for journals.
3. Replace hidden buttons with a visible lock state: "Locked because <reason>. You can: cancel, reissue, credit note" (permission-aware).
4. Allow document dates inside an open period (the owner-approved back-dating rule), at least for catch-up entry and for replacement documents.
5. Make the freeze data-driven (a per-document policy table: editable states, correction actions, numbering behaviour) so adding a document type does not mean re-implementing the matrix.

### 5.5 Design rules TEAS 2 should adopt (generic lessons from the bug classes above)

1. Model every query as **loading / empty / denied / error**; never `data ?? []`. One wrapper for lists, details and widgets.
2. One **route-to-permission manifest** drives nav, route guard, button visibility and API policy; test every role x route. Design read / write / lookup permission tiers up front (TEAS 1 needed a retro read / manage split and a name-only employee lookup).
3. Widgets and pickers **declare the permission they need** and hide / explain themselves when it is missing.
4. **Merge, never replace** asynchronously loaded defaults over user input; always say why a control is disabled.
5. **Idempotent creates**: draft id kept in form state; `Idempotency-Key` on browser creates; timeouts that say "not confirmed" instead of failing silently.
6. **One session-expiry flow** that re-authenticates the same user and preserves form state.
7. **One clock** (Asia/Bangkok) and **one basis statement** ("as of" vs "period") printed on every report; dates shown in BE with the CE input echoed.
8. **One validation source**: client and server share limits (reason length, BU required, tax-id checksum); typed 4xx, never DB 500.
9. **No raw enum or i18n key on screen or on a legal document**; key-parity tests; render legal documents from the same model as the screen (void, 10+ lines, non-VAT cases).
10. **Percent inputs** are typed percents with bounds, re-validated server-side.
11. **One dialog, one combobox, one money input, one table, one form shell** - built once, with keyboard support, focus management and ARIA, and used everywhere.
12. **Fail at setup, not at export**: filing prerequisites (registered address, SSO employer account, payee names) are checked when the data is entered or in a readiness checklist.

## Appendix A. Business rules and state machines visible in the UI (parity-critical)

### A.1 Numbering and dates

- Format `MM-YYYY-<PREFIX>-<BU code>-NNNN`; sequence is **gap-free, per company, per BU and per month of the document date**; a voided / cancelled document keeps its number and numbers are never reused. Prefixes: QT, SO, DO, IV (billing note), TI, RC, CN, DN, PO, PV (adds a category segment: `MM-YYYY-PV-{BU}-{CATEGORY}-NNNN`), VI, WT (50ทวิ, `MM-YYYY-WT-NNNN`), EX (expense claim), FA, PR (payroll run), JV (manual journals), `DEP-YYYYMM` (depreciation JE reference).
- **Number assigned at:** Q = Send; SO = Post; DO = Issue; BN = Issue; TI = Post; RC = Post; CN/DN = Post; PO = Approve; PV = Post (50ทวิ numbers in the same transaction); VI = Post; EC = Pay; FA = Activate (no JE); JV = creation; payroll run = Post.
- **Document date:** locked to "today in Asia/Bangkok" for TI, RC, CN/DN, PV, VI, PO (server re-pins at post for TI, PV, PO; a Receipt draft is NOT re-pinned at post, so a stale draft posts with its creation date; a VI is not re-pinned, so a Draft in a later-closed month cannot be posted); editable for Q, SO, DO, EC; BN editable at create but re-pinned to today on every draft save; journals `max=today`; a cancel-and-reissue replacement keeps the ORIGINAL date and posts under the original month's sequence even if that month is closed.
- Buddhist-Era display everywhere (`dd/MM/yyyy+543`, "20 พ.ค. 2569"); inputs are native CE with a BE echo.

### A.4 VAT, line math and non-VAT behaviour

- Server math per line (all 2 dp, away from zero): `gross = round(qty x price)`; `net = disc > 0 ? round(gross x (1 - d%)) : gross`; `vat = round(net x rate)`; header totals = sums of per-line results. Tax-inclusive mode exists server-side (`vat = round(total x rate / (1 + rate))`) with no UI. The server resolves rate + code from the tax-code master / product type and ignores a client rate when a code or product is present; for non-VAT companies it forces rate 0 and code VAT0.
- Rates: standard rate comes from company master data via `/system/info` (7% default); exempt product types carry 0; zero-rated is a tax code, not a rate dropdown.
- **Non-VAT company:** TI / CN / DN / ภ.พ.30 hidden; no VAT column or rows on sales and PO / PV forms; BN becomes a revenue document (issue posts Dr AR / Cr Sales; cancel reverses); RC modes become standalone cash bill or apply-to-BN; purchase VAT is forced non-recoverable and folds into cost (VI, expense claim, PV guards); ภ.พ.36 is still required (reverse charge binds non-VAT payers; the JV debits the irrecoverable-VAT expense account instead of 1170).
- **Purchase VAT rules:** vendor not VAT-registered -> input VAT must be 0 (`pv.vendor_not_vat_registered`, ม.82/5); exempt product + VAT > 0 refused (ม.81); any rate must be 0 or the company standard (`pv.vat_rate_invalid`); non-recoverable categories (ม.82/5, e.g. entertainment, vehicles) flagged and expensed; claim period (ม.82/4) = TI month .. +6.

### A.5 Withholding tax

- **Payment voucher (we withhold):** WHT type + rate per LINE on the pre-VAT net; payer mode per DOCUMENT: DEDUCT (income = net, tax = round(net x r), paid = subtotal + VAT - WHT), GROSS_UP_FOREVER (income = round(net / (1 - r)), tax = round(income x r), paid = subtotal + VAT), GROSS_UP_ONCE (income = round(net x (1 + r))). Rate auto-fills from the type and is editable (0-30%); a rate > 0 with no type is blocked. One 50ทวิ per distinct WHT type, issued at PV post; the form is chosen by payee kind: Pnd54 type wins; Pnd2 type + individual -> ภ.ง.ด.2; otherwise individual -> ภ.ง.ด.3, corporate -> ภ.ง.ด.53. No ฿1,000 threshold exists in code. Foreign vendor without Thai VAT-D: forced self-withhold gross-up (15%, ภ.ง.ด.54) and the ภ.พ.36 flag.
- **Seeded WHT types (per company, effective-dated):** RENT 5%, SVC 3%, SVC-IND 3%, ADS 2%, PROF 3%, TRANS 1%, COMM 3%, ROYAL 3%, INT 1%, INT-IND 15% (PND2), PRIZE 5%, AGRI 0.75%, ENTERTAIN 5%, CONTRACT 3%, FOR-SVC 15% (PND54), FOR-ROYAL 15% (PND54). Rate changes create a new effective-dated row.
- **Receipt (customer withholds from us):** per-line WHT by income type (base suggested from service lines, pro-rated for partial payment); total WHT <= amount (`rc.wht_exceeds_amount`); `CashReceived = Amount - WHT`; certificate rows written as `Direction='R'`; the customer's 50ทวิ number can be entered later on the receipt (chase list `missing-wht-cert`).

### A.6 GL postings (reference)

TI post: Dr AR (gross) / Cr Sales (subtotal) / Cr Output VAT. BN issue (non-VAT only): Dr AR / Cr Sales. RC post: Dr Cash or Bank (cash received) + Dr WHT receivable / Cr AR per TI or accrued BN application, or Cr Sales for a DO application, a not-yet-accrued BN or a standalone cash bill. CN post: Dr Sales return (net) + Dr Output VAT / Cr AR. DN post: Dr AR / Cr adjustment (net) + Cr Output VAT. Cancel: exact mirror of the original JE. VI post: Dr expense (+ VAT when non-recoverable or no input VAT) + Dr input VAT / Cr AP. PV post (standalone): Dr expense + input VAT (+ Dr WHT on the first line's expense account when self-withholding) / Cr WHT payable / Cr Cash (Cash method) or the company default bank GL; PV linked to a VI: Dr AP (subtotal + VAT) instead of expense. Expense claim pay and fixed-asset / depreciation entries as in A.2. ภ.พ.36 finalise: Dr 1170 / Cr 2151 (VAT companies).

### A.7 Payroll rules

SSO = 5% of salary clamped to 1,650-17,500 (maximum 875), employer equals employee; the PIT SSO allowance is capped at 10,500; allowances: personal 60,000, spouse 60,000 (married and spouse has no income), 30,000 per child; PIT is ม.50(1) projected-annual: projected income - 50% (cap 100,000) - allowances, bands 0% to 150 K then 5 / 10 / 15 / 20 / 25 / 30 / 35%, monthly withholding = (annual tax - YTD withheld) / remaining months; opening YTD applies only when its year equals the run year; calendar-day proration for mid-month joiners / leavers; "other deductions" capped at gross - PIT - SSO. Outputs: payslip PDF, ภ.ง.ด.1 PDF, สปส.1-10 (TIS-620 file + PDF + on-screen part 2), per-employee annual 50ทวิ, ภ.ง.ด.1ก yearly. Journal: Dr 5400, 5410 / Cr 2153, 2160, 2170; pay Dr 2170 / Cr 1120 or 1110.

### A.8 Bank import and reconciliation rules

KBiz (KBank) CSV (UTF-8 BOM, metadata read by Thai label, dates DD-MM-YY CE) and K PLUS PDF (positional extraction, optional password); size / MIME limits; integrity triple-check (each line amount equals the balance delta, totals match, opening + in - out = closing); a statement account number different from the selected account is rejected (digits only); overlapping periods warn only; the raw file is stored as an attachment and the password is never persisted. Suggestions: +-7 days, exact amount, posted and unmatched, ranked by bank account then nearest date. Report difference = statement closing - (GL balance - deposits in transit + outstanding payments + unmatched net), cumulative as of `to`.

### A.9 Compliance rules the UI must keep (from earlier testing and specs)

- **Immutability:** posted fiscal documents have no edit / delete route; corrections via CN/DN or cancel + reissue; warning shown at post (ม.86/4, 86/12). **Particulars:** VAT customer needs a 13-digit tax id + 5-digit branch (ม.86/4 #3); VAT-registered domestic vendor needs a tax id; company address must match registration; tax-id checksum validated (vendor / server; customer client check is regex only).
- **Cancel / replace:** replacement total amount locked (descriptive fields only); value changes go to CN/DN; customer non-payment is bad debt (ม.82/11), not cancel; cancelled TI listed as ยกเลิก 0.00 in the sales-tax report; a receipt must be cancelled before its TI; an e-Tax-submitted TI cannot be cancelled; a cancel does not amend a filed ภ.พ.30 (warn only); every cancel is reason-coded and activity-logged.
- **CN/DN:** needs a linked original TI; reason printed in Thai, never a raw code. **Settlement:** only a posted receipt settles an invoice; a receipt cannot exceed the outstanding amount (`rc.overpaid`); a PV cannot over-settle a VI.
- **ภ.พ.36 (ม.83/6):** once per service at payment in the payment month. **ภ.พ.30:** preview and finalise are separate permissions (chief / admin finalise), VAT registrants only, must tie to the tax summary, VAT register and TB to the satang, finalised payload is a snapshot.
- **Closed periods:** every GL poster refuses a closed period. **Maker-checker:** permission-based, not creator != approver; write buttons hidden. **Tenant isolation:** EF filter + DB RLS; company switcher super-admin only. **Agents:** drafts only (no `.post` scopes). **Money precision:** two-decimal satang at the posting seam. **Audit:** every state change writes an append-only activity log (5-year retention target).
